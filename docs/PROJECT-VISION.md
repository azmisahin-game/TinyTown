# TinyTown — Project vision

## One-sentence definition

TinyTown is a small, cross-platform-minded C++ procedural-world studio where people can explore a tiny city, observe autonomous agents doing understandable work, and eventually capture that world as shareable media.

## Why this project exists

The repository began from a small Win32/OpenGL C++ prototype: a window, a first-person camera, procedurally placed buildings, simple collision checks, keyboard input, and a render/update loop all lived in one source file. That experiment matters because the underlying idea is small and directly visible. The goal is to turn it into something worth reopening and sharing, without hiding its core under a large engine or an elaborate framework.

TinyTown is also a living example for future contributors and coding agents. It should answer, by running rather than by making claims:

- Can a C++ program create a visually appealing environment without imported art assets?
- Can it animate and simulate agents without an LLM?
- Can its core logic remain testable and portable?
- Can a user get a useful output from the project, not just watch a demo?
- Can optional AI/media integrations be added later without making the base application dependent on them?

## Product shape

The product has three layers, introduced in this order:

1. **World** — a compact, stylized, procedurally built town with satisfying movement, clear depth, subtle animation, and a deliberate visual style.
2. **Agency** — a small number of visible agents with goals, routes, state transitions, and inspectable task outcomes. Initial agents use ordinary deterministic algorithms, not a language model.
3. **Capture** — an output path for still images and eventually short animation clips with generated ambience. A user should be able to take something away from the session.

A future website explains the design and provides a browser demo or release downloads. The website must show real current capabilities and link to tests/builds; it must not imply that optional future AI integrations already exist.

## Relationship to Calm Haven

Calm Haven is a useful product-quality reference, not a template to clone. Its public README documents a clear audience and purpose, an intentionally local/no-account experience, procedural audio, a 3D-to-2D fallback, accessibility considerations, architecture documentation, tests, and GitHub Pages deployment. TinyTown should inherit the discipline of being understandable, graceful under failure, documented, and genuinely runnable.

TinyTown is a different product: it is a procedural world and simulation sandbox, not a relaxation or health product. Do not reuse Calm Haven's branding, copy, scene assets, sound palette, or imply clinical benefits.

## What TinyTown is not

- Not an attempt to prove that C++ is universally superior to other languages.
- Not a replacement for every game engine or every production pipeline.
- Not an AI model, image generator, video model, or realistic TTS engine by itself.
- Not a giant generic engine designed before one complete experience exists.
- Not a showcase whose screenshots are better than the actual application.

## Claims that must remain accurate

- “Procedural graphics” means geometry, patterns, materials, and animation are generated by code. It does not mean a generative AI model produced an image.
- “Procedural audio” means code synthesizes ambience/effects. It does not mean natural speech has been generated.
- “Video export” is only a shipped feature after the full export path has been tested. If MP4 needs FFmpeg, disclose that optional requirement and do not bundle it silently.
- “Cross-platform” must name the tested platforms. CI compilation is valuable but does not replace running the application on a real graphics-capable machine.
- “Offline” may be claimed only when all runtime dependencies required for the claimed workflow are available locally.

## Definition of a successful first public release

A stranger can read the README, follow a small set of commands, build and run the app on a documented platform, explore the town, observe agents performing tasks, understand the controls, and see accurate test/build status. The code and docs explain why each dependency exists. That is more valuable than a longer feature list.
